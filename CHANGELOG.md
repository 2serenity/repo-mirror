# Changelog

Версионирование: GitLab — голые semver-теги (`1.0.0`), потребитель пинит
`@1.0.0`, каталог сам держит частичные `@1` / `@1.2`. GitHub — отдельный
двигаемый тег `v1` для `uses: …@v1`. Пространства имён не пересекаются, поэтому
тег `1` на GitHub не заводится (он затенил бы каталожное разрешение `@1`).

Правило: тег `v1` не двигать, пока валидатор не зелёный.

## Unreleased

Изменения только в документации и обвязке: `mirror.sh` и `templates/mirror.yml`
не тронуты, компонент байт-в-байт равен `1.0.2`, semver-тег не выпускается.

Исправлено:

- **Reusable workflow не работал никогда.** У входов `on.workflow_call.inputs`
  отсутствовал обязательный `type:` — для `workflow_call` он обязателен, в
  отличие от `workflow_dispatch`, где по умолчанию `string`. GitHub не мог
  разобрать файл как workflow, поэтому не видел его триггеров и записывал
  startup failure на `push`: прогон без единой джобы. Шесть таких прогонов
  накопилось незамеченными — файл всё это время оставался валидным YAML, и
  проверка `parses as YAML` его пропускала. Тот же класс, что пропущенный
  `---` в компоненте: зелёная сборка, мёртвый артефакт.
  `ci/validate.sh` получил гард: каждый вход `workflow_call` обязан объявлять
  `type:`. 21 проверка вместо 20.
  Причина, по которой это пролежало шесть пушей, — у GitHub-упаковки не было
  своей проверки. На GitLab пайплайн компилирует компонент на каждом коммите,
  на GitHub не проверялось ничего. Закрыто двумя вещами: джоба `lint:actions`
  (actionlint, образ пришпилен по digest) и `.github/workflows/selftest.yml` —
  прогон **упакованного артефакта**, composite action, а не `mirror.sh`
  напрямую. Пир поднимается локально через `file://`, поэтому тест не требует
  ни ключа, ни секрета, ни сети и утверждает успех, а не конкретную ошибку:
  пир отстаёт на коммит → `LOCAL_AHEAD` → push → сошлись → второй прогон
  `EQUAL`. SSH-транспорт покрыт реальным прогоном на GitLab-стороне.
- **Документация описывала односторонний миррор, хотя логика симметрична.**
  `mirror.sh` при `PEER_AHEAD` пишет «opposite mirror will synchronize this
  side», то есть предполагает установку на обеих сторонах, а README, `action.yml`
  и шапка reusable workflow требовали protected-ветку как безусловное условие
  корректности. README получил раздел «Topology»: выбор режима по одному
  признаку, предусловия и режим отказа каждого (one-way — тихий стоп; two-way —
  достижимый `DIVERGED`), плюс раздел о восстановлении из `DIVERGED`.

Добавлено:

- `templates/mirror-standalone.yml` — генерируемая из того же `mirror.sh`
  джоба без `spec:` для пира на **другом** инстансе GitLab. Компонент туда не
  дотягивается: «You can only reference components in the same GitLab instance
  as your project». Значения приходят переменными проекта, а не входами.
  `ci/embed.sh` теперь рендерит оба артефакта, `ci/validate.sh` проверяет drift
  и форму обоих, пайплайн компилирует оба на каждом коммите.
- `ci/test-mirror.sh`: секции TWO-WAY — скрипт гоняется с обеих сторон, и
  передача хода `PEER_AHEAD` → `LOCAL_AHEAD` на пире проверяется фактом, как и
  устойчивость сошедшегося состояния. 17 проверок вместо 10.
- Второй джобой в `.github/workflows/selftest.yml` — вызов reusable workflow
  **так, как его вызывает потребитель**: по полному пути и по выпущенному тегу
  (`2serenity/repo-mirror/.github/workflows/mirror.yml@v1`). До этого путь
  `uses: <owner>/<repo>/.github/workflows/…@<tag>` не резолвил никто, и
  подтверждён он был только документацией. Пир — этот же репозиторий по HTTPS,
  поэтому прогон не требует ключа и достижимого приватного хоста: `classify()`
  видит один и тот же коммит с обеих сторон и выходит `EQUAL` до пуша. Джоба
  проверяет **тег**, а не HEAD, — она обязана краснеть, когда сломана ровно та
  ссылка, которой пользуются потребители.
  `ci/validate.sh` сверяет мажор в этой ссылке с CHANGELOG так же, как для
  `.github/workflows/mirror.yml`. 22 проверки вместо 21.
- Джоба `mirror-github` в `.gitlab-ci.yml`: проект зеркалит `main` в публичную
  копию `2serenity/repo-mirror` своим же компонентом, в стадии `publish` —
  после `validate` и `test`, чтобы сломанный `mirror.sh` ронял этот пайплайн,
  а не уезжал в копию, которую читают потребители. Раньше копию двигали
  ручные пуши.

Проверено фактом:

- `include: remote:` **принимает `inputs:`** и работает с файлом, содержащим
  `spec:` — документация этого не утверждает. `POST /ci/lint` на GitLab 19.1.2:
  `valid: true`, джоба материализуется. Значит сторона на чужом инстансе может
  тянуть компонент по публичному raw-URL, а не только копировать standalone.
- Один и тот же локальный компонент можно подключить **дважды с разными
  входами** — `component-selftest` (выключена) и `mirror-github` (рабочая)
  сосуществуют в одном пайплайне. `POST /ci/lint` на GitLab 19.1.2:
  `valid: true`, обе джобы в `merged_yaml`.
- Отпечатки host key `github.com` из `ssh-keyscan` сверены с публикуемыми
  GitHub через `GET /meta` — совпали все три (RSA, ECDSA, ED25519).
- Composite action исполняется на GitHub Actions: прогон `Self-test`
  33177578200 — чекаут, миррор к локальному `file://`-пиру, пир сдвинулся,
  повторный прогон no-op. Первый успешный прогон Actions в этом репозитории;
  до починки workflow туда просто не доходило.
- SSH-обвязка отработала на реальном пире, а не на `file://`: джоба 5616,
  `LOCAL_AHEAD` → `push succeeded`, GitLab → GitHub. Раньше `GIT_SSH_COMMAND`,
  ключ и `known_hosts` не покрывал ни один тест.
- **Направление GitHub → GitLab пройдено целиком на реальной паре**
  (`2serenity/mirror-probe` ↔ self-managed `mirrortest/mirror-probe`, порт
  2222), и это закрыло сразу четыре ASSUMPTION:
  * reusable workflow, вызванный **из другого репозитория** по полному пути и
    тегу, резолвится и исполняется — прогон 33179748701. Ловушка `uses: ./`
    больше не подтверждена одной лишь документацией.
  * SSH с GitHub-hosted раннера до self-managed GitLab работает:
    `From ssh://…:2222/…` в логе, `StrictHostKeyChecking=yes` совпал по записи
    вида `[host]:2222`, deploy key принят.
  * доставка `LOCAL_AHEAD` → `push succeeded` в **protected** `main` прошла —
    прогон 33179829162. Ожидание было обратным: считалось, что deploy key
    обязан быть выбран в *Allowed to push and merge*. Достаточно, чтобы там
    был выбран **хоть кто-то** и создатель ключа был участником проекта с
    доступом к коду; собственной записи `deploy_key_id` в `push_access_levels`
    не требуется. README исправлен по факту.
  * `PEER_AHEAD` на реальном SSH — прогон 33180114640: сторона отошла, exit 0,
    ничего не сдвинула.
- **Двусторонний режим подтверждён вне `file://`.** Обратная нога поставлена
  компонентом из каталога (`…/repo-mirror/mirror@1.0.2`) в стороннем проекте:
  пайплайн 2530, джоба 5643 — `LOCAL_AHEAD` → `push succeeded` в GitHub.
  Пуш deploy key'ем **запустил** Actions на приёмной стороне (прогон
  33180509119), и встречный прогон завершился `EQUAL` — передача хода
  замыкается, петли нет. До этого и права ключа, и встречный `EQUAL` были
  ASSUMPTION.
- **`glab variable set … < file` тоже срезает финальный перевод строки.**
  Сохранилось 418 байт вместо 419 — та же поломка, что у `$(cat key)`, но уже
  в самом инструменте, а не в подстановке shell. Значит проверять надо
  результат, а не способ записи: прочитать переменную обратно и сравнить длину
  с файлом. Чинится `PUT` со значением, собранным как
  `v=$(cat f; printf x); v=${v%x}`.
- Ключ в CI-переменной **обязан заканчиваться переводом строки**. `$(cat key)`
  в shell его срезает, и libcrypto отказывается разбирать результат:
  `Load key: error in libcrypto` → `Permission denied (publickey)` → exit 31.
  Симптом выглядит как проблема доступа, а не формата. Диагностика — не
  перевыпуск ключа, а `ssh-keygen -y -f` на сохранённом значении.

Известные ограничения:

- Логи `mirror.sh` при `PEER_AHEAD` после refetch по-прежнему обещают, что
  «opposite mirror will synchronize this side» — в one-way это неправда.
  Правка тронула бы `templates/mirror.yml` и потребовала semver-релиза;
  кандидат в следующий функциональный релиз.
- Приёмная ветка `main` на GitHub защищена ruleset'ом `protect-main`
  (`non_fast_forward` + `deletion`, без bypass actors). Это снимает перезапись
  и удаление, но **не** обычный прямой пуш — а в one-way молча останавливает
  доставку именно он. Сам отказ по force-push рантаймом не проверялся.
- Тег `v1` на GitHub миррор не двигает — `mirror.sh` пушит одну ветку и тегов
  не касается. Это осознанно: предки тегов `1.0.x` на GitLab содержат
  вычищенные данные.
- `git` печатает URL пира (`From …` / `To …`), поэтому адрес пира настолько же
  публичен, насколько публичны логи вызывающего репозитория. Регистрация хоста
  секретом заставляет Actions его затирать; это подпорка, а не граница.
- Обратный миррор на самой паре `repo-mirror` не установлен: GitHub-копия —
  опубликованное зеркало, в неё никто не коммитит. Направление проверено на
  отдельной паре (см. выше), а не здесь.
- Отказ ruleset'а по force-push рантаймом по-прежнему не проверялся.
- `actions/checkout@11d5960a` (v4) целится в Node 20 и на раннерах уже идёт с
  предупреждением о принудительном Node 24. Смена SHA на v5 — отдельная правка
  с перепроверкой пиннинга, не в этот заход.

## v1.0.2

Исправлено:

- **Компонент не публиковался в CI/CD Catalog.** `release`-джоба создавала
  релиз через Releases API, а каталог засчитывает только релиз, созданный
  ключевым словом `release:`. Ошибка `jobs release config should implement
  the script:/run:/trigger: keyword`, из-за которой от ключа отказались,
  означала лишь отсутствие `script:` в джобе, а не отсутствие поддержки.
  Джоба переведена на `release:` + `script:` и образ
  `registry.gitlab.com/gitlab-org/cli:latest` (GitLab 19.0 удалил fallback на
  `release-cli`, нужен glab >= v1.58.0).

Известные ограничения:

- `release`-джоба снова неидемпотентна: повторный прогон пайплайна на том же
  теге упадёт, потому что релиз уже существует. У ключевого слова нет режима
  «пропустить», а публикация в каталоге важнее.
- `registry.gitlab.com/gitlab-org/cli:latest` — единственная незафиксированная
  зависимость пайплайна; версионированного тега upstream не даёт.
- Релизы `1.0.0` и `1.0.1` в каталог не попадут: они созданы до включения
  тумблера и через API.

## v1.0.1

Исправлено:

- **`templates/mirror.yml` не подключался вообще.** Между блоком `spec:` и
  джобой не было разделителя YAML-документов (`---`), который обязателен,
  когда в файле после заголовка идут джобы. GitLab отвечал каждому
  потребителю `Given inputs not defined in the spec section of the included
  configuration file`. Релиз `1.0.0` использовать нельзя.
- **`.github/workflows/mirror.yml` не работал у потребителя.** Шаг миррора
  ссылался на `uses: ./`, а reusable workflow выполняется в воркспейсе
  вызывающего репозитория, где `action.yml` отсутствует. Теперь ссылка явная:
  `2serenity/repo-mirror@v1`.
- `release`-джоба идемпотентна: повторный прогон на существующем теге больше
  не падает на 409.

Добавлено:

- Пайплайн проекта подключает собственный компонент с `rules: [{when: never}]`
  — сломанный `spec:` или неверная интерполяция входа теперь кладут сборку
  здесь, а не у потребителя.
- `ci/test-mirror.sh` — поведенческий тест `mirror.sh` на реальных
  репозиториях: EQUAL / LOCAL_AHEAD / PEER_AHEAD / DIVERGED и коды 30/31.
  Пиры общаются по `file://`, поэтому SSH-обвязка тестом не покрыта.
- `ci/validate.sh`: проверки стали документо-зависимыми (`spec:` в документе 0,
  джоба в документе 1, ровно один `---`), плюс YAML-разбор `action.yml` и
  workflow, запрет `uses: ./`, сверка мажора в ссылке на action с CHANGELOG и
  требование SHA-пиннинга для `actions/*`.
- Вход `timeout` (по умолчанию `10m`): недоступный пир больше не держит
  `.pre`-джобу до дефолтного таймаута проекта.
- `test -n "$MIRROR_BRANCH"` в `before_script` — пустой вход больше не
  превращается молча в `main`.
- `actions/checkout` пришпилен к SHA.

## v1.0.0

**Сломан, не использовать** — компонент не подключается, см. `1.0.1`.

Добавлено:

- Первая версия. Механизм A (peer fast-forward mirror) вынесен из
  репозиториев-потребителей в переиспользуемый компонент. Источник правды —
  `mirror.sh`, одинаковый для GitLab (инлайн в компонент) и GitHub (composite
  action).
- `mirror.sh` умеет классифицировать `EQUAL / LOCAL_AHEAD / PEER_AHEAD /
  DIVERGED` и при `LOCAL_AHEAD` делает refetch + финальную перепроверку перед
  `exit 32` (доработка поведения прежней копии, где второй неудачный push
  давал безусловный `exit 32`).
- `mirror.sh` усилен SSH-таймаутами: `ConnectTimeout=10`,
  `ServerAliveInterval=15`, `ServerAliveCountMax=3` — защита от зависания
  пайплайна при недоступном пире.
- Имена секретных File-переменных (`MIRROR_SSH_KEY` / `MIRROR_KNOWN_HOSTS`)
  зашиты как контракт компонента; переименовываемые входы для них не
  предусмотрены (YAGNI).
- Для GitLab: `GIT_DEPTH:"0"` и `apk add git openssh-client` заданы внутри
  джобы, поэтому компонент не зависит от глобальных настроек потребителя.

Совместимость: первая версия, потребителей на момент выпуска нет.
