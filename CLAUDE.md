# repo-mirror — контракт и радиус поражения

## Что это

Переиспользуемый механизм зеркалирования ветки между двумя Git-репозиториями
(fast-forward-only, symmetric peer mirror). Один источник правды — `mirror.sh`.
Две упаковки:

- GitLab CI/CD Catalog component (`templates/mirror.yml`).
- GitHub composite action (`action.yml`) + reusable workflow
  (`.github/workflows/mirror.yml`).

## Жёсткий контракт

- `mirror.sh` — единственный источник правды. Править только его.
- `templates/mirror.yml` — **сгенерирован** (`ci/embed.sh`), руками не
  править. `ci/validate.sh` валит сборку при расхождении (drift).
- Имена секретных File-переменных зашиты: `MIRROR_SSH_KEY`,
  `MIRROR_KNOWN_HOSTS`. Не делать их входами.
- Обязательные входы компонента: `branch`, `peer_url`. Остальное — дефолты.
- В `templates/mirror.yml` **обязателен разделитель `---`** между `spec:` и
  джобой. Без него GitLab отвечает потребителю `Given inputs not defined in
  the spec section` — компонент нерабочий, а сборка при этом зелёная. Так
  уехал релиз `1.0.0`. Валидатор теперь это проверяет.
- В `.github/workflows/mirror.yml` **нельзя `uses: ./`**: reusable workflow
  выполняется в воркспейсе вызывающего репозитория. Ссылка на composite action
  всегда явная, `2serenity/repo-mirror@vN`, и её мажор сверяется с CHANGELOG.
- Релиз создаётся **только ключевым словом `release:`** (плюс обязательный
  `script:`) в образе `registry.gitlab.com/gitlab-org/cli:latest`. Releases
  API каталог не засчитывает — компонент останется unpublished при зелёной
  сборке. Так потерялись `1.0.0` и `1.0.1`.
- Пайплайн проекта подключает собственный компонент (`rules: [{when: never}]`).
  Это единственная проверка, которая заставляет GitLab реально разобрать
  `spec:` и интерполяцию входов. Не удалять.

## Радиус поражения

- Сломанный `mirror.sh` ломает зеркалирование у ВСЕХ потребителей сразу.
  Поэтому validate (shell + drift + self-include) и `ci/test-mirror.sh`
  обязаны быть зелёными до пуша тега, и тег `v1` не двигается, пока
  валидатор не зелёный.
- `PEER_AHEAD` → `exit 0` и ничего не делает. Если кто-то пишет напрямую в
  приёмную ветку пира, миррор молча перестаёт доставлять. Обязательное
  условие: приёмная ветка на пире **protected**, пишет только ключ миррора.
- `resource_group` не координирует GitHub↔GitLab (разные системы) — это норма
  для одностороннего миррора.

## Что НЕ решено / вне объёма

- Механизмы B и C (`mirror-to-gitlab.yml`, `import-from-gitlab.yml`) —
  односторонние MR/PR через GitLab API. Не включены в компонент, остаются
  локально в репозиториях-потребителях.
- Перевод существующих потребителей на компонент не
  выполнен — они работают как есть («работает — не трогай»).
- Самозеркалирование `repo-mirror` (GitLab → GitHub) делается встроенным push
  mirror в UI, НЕ своим же компонентом (сломанный релиз запер бы починку).
