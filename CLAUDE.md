# repo-mirror — контракт и радиус поражения

## Что это

Переиспользуемый механизм зеркалирования ветки между двумя Git-репозиториями
(fast-forward-only, symmetric peer mirror). Один источник правды — `mirror.sh`.
Три упаковки:

- GitLab CI/CD Catalog component (`templates/mirror.yml`).
- GitHub composite action (`action.yml`) + reusable workflow
  (`.github/workflows/mirror.yml`).
- Standalone-джоба (`templates/mirror-standalone.yml`) — для пира на **другом**
  инстансе GitLab, который компонент подключить не может в принципе.

Одна установка только пушит. Двусторонний миррор — это **две независимые
установки**, по одной на сторону, а не один двунаправленный процесс. Выбор
топологии и его последствия — в README, раздел «Topology».

## Жёсткий контракт

- `mirror.sh` — единственный источник правды. Править только его.
- `templates/mirror.yml` и `templates/mirror-standalone.yml` —
  **сгенерированы** (`ci/embed.sh`), руками не править. `ci/validate.sh` валит
  сборку при расхождении (drift) по обоим.
- Компонент не резолвится между инстансами: «You can only reference components
  in the same GitLab instance as your project». Поэтому standalone-артефакт —
  не удобство, а единственный способ дать логику стороне на чужом инстансе.
  Правило прежнее: это копия релиза, а не форк логики.
- Имена секретных File-переменных зашиты: `MIRROR_SSH_KEY`,
  `MIRROR_KNOWN_HOSTS`. Не делать их входами.
- Обязательные входы компонента: `branch`, `peer_url`. Остальное — дефолты.
- В `templates/mirror.yml` **обязателен разделитель `---`** между `spec:` и
  джобой. Без него GitLab отвечает потребителю `Given inputs not defined in
  the spec section` — компонент нерабочий, а сборка при этом зелёная. Так
  уехал релиз `1.0.0`. Валидатор теперь это проверяет.
- В `.github/workflows/mirror.yml` **нельзя `uses: ./`**: reusable workflow
  выполняется в воркспейсе вызывающего репозитория. Ссылка на composite action
  всегда явная, `2serenity/repo-mirror@vN`, и её мажор сверяется с CHANGELOG.
- Релиз создаётся **только ключевым словом `release:`** (плюс обязательный
  `script:`) в образе `registry.gitlab.com/gitlab-org/cli:latest`. Releases
  API каталог не засчитывает — компонент останется unpublished при зелёной
  сборке. Так потерялись `1.0.0` и `1.0.1`.
- Пайплайн проекта подключает собственный компонент (`rules: [{when: never}]`)
  и standalone-артефакт (гасится переопределением джобы `mirror`). Это
  единственная проверка, которая заставляет GitLab реально разобрать `spec:` и
  интерполяцию входов. Не удалять.
- Проект зеркалит сам себя своим же компонентом: джоба `mirror-github` в
  стадии `publish`, `main` → `2serenity/repo-mirror`. Стадия выбрана не по
  вкусу — в дефолтной `.pre` миррор ушёл бы в публичную копию раньше, чем
  `validate` и `test` успели сказать, что коммит вменяем.
- **Теги на GitHub не зеркалируются и не должны.** Предки тегов `1.0.0`–`1.0.2`
  (`80066ba`, `a9397b9`) содержат реальный хост, SSH-порт и `FIX_PLAN.md`.
  `mirror.sh` пушит ровно один ref и тегов не касается — это и есть гарантия.
  Встроенный push mirror GitLab здесь применять нельзя: он гонит теги.
  Тег `v1` на GitHub по-прежнему двигается руками.
- Истории обеих сторон унифицированы 2026-08-28: `main` на GitLab перезаписан
  чистой историей (`283b45f`), старая лежит в `backup/pre-unify`. До этого у
  сторон не было общего предка и миррор давал бы `DIVERGED` на первом прогоне.

## Радиус поражения

- Сломанный `mirror.sh` ломает зеркалирование у ВСЕХ потребителей сразу.
  Поэтому validate (shell + drift + self-include) и `ci/test-mirror.sh`
  обязаны быть зелёными до пуша тега, и тег `v1` не двигается, пока
  валидатор не зелёный.
- `PEER_AHEAD` → `exit 0` и ничего не делает. Что это значит — зависит от
  топологии, и подменять одно другим нельзя:
  - **one-way**: доставка встала. Прямой пуш в приёмную ветку пира молча
    останавливает миррор при зелёном пайплайне. Обязательное условие —
    приёмная ветка на пире **protected**, пишет только ключ миррора.
  - **two-way**: это передача хода, встречный миррор доставит. Взамен
    `DIVERGED` (exit 20) становится штатно достижимым и чинится руками.
    Автоматического разрешения не будет: любое теряет чьи-то коммиты.
- `resource_group` (GitLab) и `concurrency` (GitHub) координируют только свою
  сторону. Общего лока между двумя системами нет — в two-way это заметнее.

## Что НЕ решено / вне объёма

- Механизмы B и C (`mirror-to-gitlab.yml`, `import-from-gitlab.yml`) —
  односторонние MR/PR через GitLab API. Не включены в компонент, остаются
  локально в репозиториях-потребителях.
- Перевод существующих потребителей на компонент не
  выполнен — они работают как есть («работает — не трогай»).
